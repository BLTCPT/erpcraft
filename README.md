# ERPCraft

**A free, open-source, clean-room ERP in Rust — AI-native from day one.**

ERPCraft takes the ArtCraft playbook — clean-room rebuilds of expensive,
closed incumbents, in pure Rust, with the source open — and applies it to
enterprise resource planning. The full vision is a complete ERP: general
ledger, order-to-cash, purchasing, inventory, manufacturing, and reporting,
owned by the people who run it, offline-capable, with no license fees and no
1990s workflows held together by million-dollar consultants.

This repository is the working core of that vision, being built in the open:
a **double-entry ledger that is provably correct**, the order-to-cash loop on
top of it, and an AI agent that drives the same commands a human does.

> ERPCraft is a clean-room implementation written from scratch. It is not
> affiliated with, endorsed by, or derived from SAP SE or any other ERP
> vendor.

## Status: early alpha — the working core, provably correct

Honest framing, in the Storytold tradition: this is an early alpha, not a
daily-driver replacement for a production ERP. What exists today is the
foundation everything else stands on, and it is built to be *verified*, not
trusted:

- **Chart of accounts** — seeded for a small manufacturer (22 accounts;
  the procure-to-pay seed adds GR-IR clearing and purchase price
  variance, so a fully seeded database reports 24).
- **Double-entry journal** — the core invariant (*every posting balances,
  debits = credits*) is enforced **in the database itself** (SQLite
  triggers), not just in application code. No code path — HTTP, CLI, MCP, an
  AI agent, or raw SQL — can post an unbalanced entry.
- **Append-only ledger** — posted entries are immutable at the DB level.
  Corrections are reversing entries that reference the original. The full
  history replays from the journal.
- **Money is integer cents** — never floating point.
- **Order-to-cash with a GL posting engine** — quotes → sales orders →
  invoices → payments → returns, with revenue/COGS/payment/reversal
  postings generated by the transitions themselves. The hand-computed
  "oracle day" (ending trial balance **$129,975.00 per side**) is the
  acceptance suite.
- **Variant configurator** — SAP LO-VC-style object dependencies
  (precondition / selection condition / constraint) as a typed AST,
  evaluated deterministically in the core; selected components roll into
  line price *and* standard cost. AI only authors (behind
  propose → confirm) and explains. See `CONFIGURATOR_DESIGN.md`.
- **One dispatch table, four doors** — 58 commands served identically to
  the operator CLI, an MCP server on stdio, the HTTP API, and the agent.
  JSON out, plain-language refusals, exit 0/1/2.
- **Natural-language agent** — turns plain English into *proposed*
  dispatch calls, renders the confirmation from ledger data (never from
  model prose), and posts only after a human confirms. The parse route
  is exercised live against Baseten's `muse-spark-open-1026` (hackathon
  grant); the shipped demo fixture is recorded from that live model.
- **Audit trail (Day 6)** — every journal entry explains itself: who
  posted it, which document it belongs to, why it posted, the full
  provenance chain (quote → order → invoice → payments → returns) with
  reversal links both ways, and — for agent postings — the verbatim
  human prompt that proposed it.
- **AI-native MRP (Day 7)** — materials planning on the Warp Speed
  pattern: *dynamic* (every run recomputes from current orders, stock,
  BOMs, and configurations — plans are never stored), *explainable*
  (every planned order carries its netting math and demand reasons; a
  shortage is a planned order whose start date already passed), and
  *agent-native* (dispatch/MCP commands plus NL questions — "Can we
  build 200 BRK-100 by Nov 15?" — and gated release of planned orders).
  See `MRP_DESIGN.md`.

## The demo company

The seed data is **Cascade Precision Parts**, a fictional small Oregon
manufacturer making metal brackets (standard cost $68.00/unit). Customers in
the scripted demo day: Acme, Beta, Delta, Epsilon. Opening trial balance:
$120,500.00 on both sides. The scripted "oracle day" — 14 posting
transactions whose ending trial balance ($129,975.00) is hand-computed —
becomes the acceptance test suite for the posting engine.

## Quickstart

```sh
cargo test                    # the invariant suite — start here
cargo run -p erpcraft-server  # serves on http://127.0.0.1:3000
```

Then:

```sh
curl localhost:3000/health
curl localhost:3000/trial-balance
# Post a balanced entry (Dr Cash $100.00 / Cr Sales Revenue $100.00):
curl -X POST localhost:3000/journal-entries -H 'content-type: application/json' -d '{
  "entry_date": "2026-10-26", "memo": "Manual sale", "source": "manual",
  "lines": [
    {"account_code": "1000", "debit_cents": 10000},
    {"account_code": "4000", "credit_cents": 10000}
  ]}'
# Try an unbalanced one — the database itself refuses it (HTTP 400):
curl -X POST localhost:3000/journal-entries -H 'content-type: application/json' -d '{
  "entry_date": "2026-10-26", "memo": "One cent short", "source": "manual",
  "lines": [
    {"account_code": "1000", "debit_cents": 10000},
    {"account_code": "4000", "credit_cents": 9900}
  ]}'
```

Environment: `ERPCRAFT_DB` (default `erpcraft.db`), `PORT` (default `3000`).

The CLI door, against the same database:

```sh
cargo run -p erpcraft-cli -- trial_balance
cargo run -p erpcraft-cli -- help        # all 58 commands
cargo run -p erpcraft-cli -- mcp         # the same table as MCP tools on stdio
```

## The demo script

A five-minute walkthrough of the whole system (fresh database):

```sh
export ERPCRAFT_DB=/tmp/demo.db; rm -f $ERPCRAFT_DB
E="cargo run -p erpcraft-cli --"
```

1. **Seed + health.** `$E health` — Cascade Precision Parts is
   seeded (24 accounts, 4 customers, and the MRP scenario: BRK-100
   BOM, stock, lead times). `$E trial_balance` — the opening books
   balance at $120,500.00 per side.
2. **Configured quote.** A BRK-100 in steel with a galvanized finish:
   the configurator forces the reinforced mount (a named constraint)
   and rolls the selected components into the line price —
   $162.00/unit:
   `$E create_quote --json '{"customer_id":1,"lines":[{"item_id":1,"qty":50,"configuration":{"material":"steel","finish":"galvanized"}}]}'`
   then `$E send_quote 1`, `$E accept_quote 1`, `$E create_order 1`.
   Ask for the impossible variant and it refuses, with its reason:
   `$E evaluate_config --json '{"model_id":1,"configuration":{"material":"aluminum","finish":"galvanized"}}'`
   — "Galvanized finish is available only on steel brackets."
3. **Agent invoice.** `$E agent "Invoice Acme for the 40 units we
   shipped Tuesday."` — the agent proposes; the confirmation shows
   the $5,000.00 posting rendered from the ledger (debits = credits
   $7,720.00 with COGS); nothing posts until you confirm at the
   prompt (`--yes` confirms after printing, for scripts).
4. **MRP check.** `$E agent "Can we build 200 BRK-100 by
   2026-11-15?"` — a live plan, computed on the spot from current
   state: total demand is 250 (the open order from step 2 plus your
   200), 50 are covered, so the plan builds 200 more starting
   Nov 10. The full plan (`$E run_mrp --demand-sku BRK-100
   --demand-qty 200 --demand-date 2026-11-15`) also nets the
   components: purchases of 30 steel blanks and 110 fastener sets.
   Run `$E explain_shortage --sku FST-SET --as-of 2026-11-12
   --demand-sku BRK-100 --demand-qty 200 --demand-date 2026-11-15`
   to see the fastener order become a *shortage* once its start
   date (Nov 7) has passed — anticipation, not a stored report.
5. **Gated release.** `$E agent "Release purchase:FST-SET:2026-11-10:110
   from the 200 BRK-100 by 2026-11-15 plan."` — propose → confirm
   creates the purchase-order *document* and counts the units as
   on-order supply in the next run. No journal entry posts; value
   moves only when the supplier is paid.
6. **Audit trail.** `$E agent --yes "Buy $3,600 of raw materials on
   credit."`, then `$E audit_trail --source agent` — the entry the
   agent posted, who posted it, and your verbatim prompt. And
   `$E audit_entry <id>` walks any entry's provenance chain
   (quote → order → invoice → payment → return reversal), e.g. the
   revenue entry of the invoice from step 3.

## Hard rules (decided once, not revisited)

1. Money is never f64 — integer minor units everywhere.
2. The double-entry invariant is enforced in the DB layer.
3. The journal is append-only; corrections are reversing entries.
4. The agent never posts unconfirmed: propose → show the journal lines in
   plain language → human confirms → post.
5. Every command has a test; the oracle day's hand-computed trial balance is
   the acceptance suite.
6. Deterministic core, AI at the edges: the configurator evaluator and
   the MRP planner are pure functions of current state; models only
   parse, author (behind the gate), and explain.
7. Plans are never stored, and planning never posts: MRP releases
   create documents; the GL moves only through the posting map.

## Layout

- `crates/erpcraft-core` — the deterministic core: ledger (schema +
  invariant triggers, posting engine, trial balance), order-to-cash,
  the variant configurator, the audit trail, and MRP.
- `crates/erpcraft-server` — Axum HTTP server over the core.
- `crates/erpcraft-cli` — the dispatch table (CLI + MCP doors), and
  the natural-language agent over it.
- Design docs: `CONFIGURATOR_DESIGN.md`, `MRP_DESIGN.md`; parked
  ideas live in [ROADMAP.md](ROADMAP.md).
